# 自然言語対話・問い合わせ応答（F8）詳細設計 v1.0

最終更新: 2026-07-25
前提: 要件 `docs/requirements.md` §F8、MVP `docs/mvp-design.md` §4.3（メンバー応答）

---

## 1. 目的・スコープ

会員がLINEで自由文で聞いたこと（「次の例会いつ？」「会場どこ？」「自分の出欠どうなってる？」）に、
**自LOMの実データに基づいて**答える。答えられないものは専務・事務局へ取次ぐ。

| 要件 | 内容 | 優先 | 実装 |
|---|---|---|---|
| F8-1 | 自由文の問い合わせに Gemini で応答 | MUST | ○ |
| F8-2 | 自LOM情報に基づき生成（RAG）し、根拠の薄い断定を避ける | MUST | ○ |
| F8-3 | 扱えない依頼は専務/担当へエスカレーション | MUST | ○（`Escalation` 起票） |
| F8-4 | 他者の個人情報の不適切な開示を拒否するガード | MUST | ○（§3） |
| F8-5 | 直近のやり取りの文脈を保持 | SHOULD | ○（直近3往復） |

現状（本設計の前）は、キーワードに当たらない入力は**メニューを返すだけ**だった。
本設計はその「最後の分岐」を自然言語応答に置き換える（キーワード一致の既存動作は維持）。

---

## 2. 処理の流れ

```
LINEテキスト
  ├─ 招待コード未連携 → 本人確認（既存）
  ├─ キーワード一致（予定/出欠/事務局/メニュー）→ 既存の定型応答
  └─ それ以外 ─► [RAGコンテキスト構築] ─► [Gemini] ─► JSON{answer, grounded, needs_human}
                    │                                      │
                    │                          grounded=false or needs_human=true
                    │                                      ▼
                    └─ LLM未設定/失敗 → メニュー誘導      Escalation 起票＋「事務局に取次ぎました」
```

- LLM が使えない環境（ローカル/テスト/障害時）は**従来どおりメニュー誘導にフォールバック**。落とさない。
- 生成のトークンは `InferenceLog(kind="member_qa")` に記録し月間コストKPIへ合算。

---

## 3. コンテキスト（`app/rag.py`）と個人情報ガード

コンテキストに**入れるもの**（＝答えられる範囲）:
- 質問者自身の情報（氏名・所属委員会・役職）
- 直近・次回のイベント（日時・場所・締切・自分が対象か・**自分の**出欠）
- 自分に割り当てられた対外連絡の未対応タスク
- 配信済み対外連絡の要約（件名・要約・期限）

**入れないもの**（F8-4 の一次防御）:
- 他会員の氏名・連絡先・LINE ID・出欠状況・個人別の対応状況

> ガードの考え方: **プロンプトの禁止指示だけに頼らず、そもそも他者の個人情報をコンテキストに載せない**。
> 載っていない情報は漏れない。加えてプロンプトでも「他の会員の個人情報は答えず事務局に案内する」と明示する。

---

## 4. データモデル（追加）

```
conversations/{memberId}
  member_id: str
  turns: [{ at, role: "user"|"assistant", text }]   # 直近 MAX_TURNS(6) 件のみ保持
  updated_at: datetime
```
文脈は「直近3往復」程度に限定する（長期記憶は持たない＝誤参照と保持リスクを避ける）。

---

## 5. LLM 出力契約

```json
{ "answer": "会員への返信文（敬体・200字以内）",
  "grounded": true,      // 提供情報だけで答えられたか
  "needs_human": false }  // 人（専務・事務局）の対応が必要か
```
- `grounded=false` または `needs_human=true` → `Escalation(kind="question")` を起票し、取次メッセージを添えて返す。
- 「わからない」ときに推測で答えないことをプロンプトで強制する（F8-2）。

---

## 6. 管理側の受け口（F8-3）

| メソッド/パス | 用途 |
|---|---|
| GET `/api/escalations?status=open` | 取次依頼・答えられなかった質問の一覧（会員名を補完） |
| POST `/api/escalations/{id}/handled` | 対応済みにする（監査 `escalation.handled`） |

管理SPAのホームに「取次・問い合わせ」カードとして表示し、その場で対応済みにできる。

---

## 7. チャットで届いた出欠の連絡（F4-7）

「本日の五役は欠席になりそうです」「やっぱり参加難しいです」のような**出欠の連絡**には、
AI で読み取らず、LIFF「予定と出欠」（`?view=events`）を開くボタンと
「出欠の登録・変更は［予定と出欠］の画面からお願いします。チャットのメッセージでは出欠は変わりません。」
を返す。グループのメンションでは、誰あての案内か分かるよう先頭に名前を付ける。

- 判定は言葉だけで行う（出席・欠席・参加・休み・行けない・遅れ・遅刻・早退など）。
  「？」「何」「いつ」「ですか」などを含む質問の文は対象外にし、これまでどおり AI が答えて［予定と出欠］を添える。
- LIFF が未設定のときは、トークに予定と出欠の案内を返すボタン（`menu|予定と出欠`）にする。
- リッチメニュー由来の定型（`menu|出欠を回答`）はこれまでどおり。

**背景（2026-11-05）**: 1 対 1 のトークで届いた欠席の連絡に AI の返事とボタンを返すだけだったため、
本人は連絡が済んだと思い、出欠が変わらないままになった。AI で読み取って確認のうえ登録する案も試したが、
出欠の変更は LIFF の画面に既にあるので、画面へ案内するほうが単純で間違いがないと判断した。

---

## 8. 運用上の注意

- 会員向け応答は**助言ではなく事実回答**なので、根拠のない断定を避ける設計（§5）が要。
- エスカレーションは管理画面ホームの「要対応」に件数が出る（既存 `open_escalations`）。
- 応答文は200字以内。長文はLINEで読みにくく、誤読の元になる。
